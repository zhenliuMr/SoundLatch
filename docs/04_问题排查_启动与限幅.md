## 1. 启动无反应

### 1.1 兼容性排查：不是 Win10/11 的问题

| 检查项 | 结果 |
|---|---|
| PE 类型 | PE32+ (x64)，Subsystem 5.2，Windows GUI |
| 依赖 | 全部系统 DLL + `api-ms-win-crt-*`（UCRT，Win10 起随系统自带） |
| 是否有新版 API | 无。USER32/SHELL32 导入全部是 Vista/7 时代函数；`Shell_NotifyIconGetRect` 最早 Win7 |
| 静态链接 | `-static -static-libgcc -static-libstdc++`，无 MinGW 运行库依赖 |
| 清单 | `asInvoker`（不需要管理员）、DPI permonitorv2、supportedOS 声明 Win10/11 |
| 实测 | Win11（本机）启动、托盘、引擎、面板全部正常 |

→ **不存在「Win10 能开、Win11 不能开」这类兼容性差异。**

### 1.2 真正原因：首启不显示任何 UI（可复现）

`src/main.cpp:1470`

```cpp
if (w == 9) {              // 启动后静默建好面板（不开窗），只为了把引擎跑起来
    KillTimer(h, 9);
    EnsurePopup();          // 只创建隐藏窗口，没有 ShowPopup()
    return 0;
}
```

注释写的是「再弹面板」，但代码只调 `EnsurePopup()`（`CreateWindowExW` 不带 `WS_VISIBLE`）。实测枚举该进程的顶层窗口：

```
== 首次启动（pid 14496）==
  cls=SoundLatchPopup   vis=False  rect=0,0 320x320     ← 面板存在但不可见
  cls=SoundLatchWnd     vis=False  rect=0,0 0x0         ← 消息窗
  cls=SoundLatchBubble  vis=False
  <无任何可见窗口>
== 再点一次 exe ==
  cls=SoundLatchPopup   vis=True   rect=1152,647 278x363  ← 这次才出现
```

即：**用户点一次 = 屏幕上什么都不会出现**。唯一信号是托盘图标，而 Win10 和 Win11 都把新托盘图标默认折叠进「显示隐藏的图标」溢出区（Win11 更彻底，默认全部折叠）。用户看不到图标，自然判断「打不开、点了没反应」。

这不是用户误判 —— 是首次启动缺少可见反馈。README 写「启动后驻留托盘，点图标展开面板」，用户不知道要去溢出区找。

### 1.3 另有三条真实存在但无法本地复现的路径

| 路径 | 机理 | 如何确认 |
|---|---|---|
| SmartScreen / Defender 拦截 | exe 未签名，GitHub 直链下载带 MOTW。Win10/11 默认「基于声誉的保护」对低信誉未签名 exe 会在启动前拦下，点「不运行」或直接被隔离 → 双击无任何反应，进程都不存在 | 让用户看任务管理器有没有 SoundLatch.exe；`Get-MpThreatDetection` 查隔离记录 |
| UIPI 拦消息 | 若已有一个**管理员权限**实例在跑，普通权限下再点 exe：互斥体同名 → `FindWindow` 找到 → `PostMessage(WM_SHOWPOPUP)` 被 UIPI 静默拒绝（返回 FALSE，代码没检查）→ 新进程 `return 0` 退出，旧实例毫无反应 | 代码可改：检查 `PostMessageW` 返回值 |
| 托盘图标加失败 | `TrayAdd()` 没检查 `Shell_NotifyIconW` 返回值，Explorer 未就绪时静默失败；只有 `TaskbarCreated` 广播才会补加 | 同上，可加返回值检查 + 重试 |

### 1.4 顺带发现：日志不可用于远程排障

`slLog()` 用 `vswprintf(buf, 512, fmt, ap)`，而这套 MinGW 运行时的宽字符 `%s` 按**窄字符串**解释，实测日志：

```
engine started: cap={ ren=lbðXhV  loop=0 lat=254.8ms     ← 设备名全部丢失
```

用户回传日志时看不到设备，等于没有诊断信息。改 `%ls` 即可（另建议把日志文件名从 `soundlatch_theme.log` 改成 `soundlatch.log`，并加启动首行 `build/时间/命令行` 标记）。

### 1.5 建议修复（按优先级）

1. `WM_TIMER(9)` 里 `EnsurePopup()` 之后判断是否首次运行（config 不存在），是则 `ShowPopup(false)`（不抢焦点）—— 一次改动解决主诉。
2. 即便不弹面板，也要给可见反馈：`NIF_INFO` 气泡「SoundLatch 已在托盘运行，点图标打开面板」。
3. `TrayAdd()` 检查 `Shell_NotifyIconW` 返回值，失败时 500 ms 后重试 3 次。
4. 单实例转发检查 `PostMessageW` 返回值，失败则退回本地启动（避免被 UIPI 吃掉）。
5. 发布页说明「未签名 → 可能出现 SmartScreen 提示」，附 SHA256；有条件的做代码签名。

## 2. 锁定最大输出：「掩盖脚步 / 闷响」

### 2.1 先厘清两件事

- 面板上的开关叫 **「锁定最大输出音量」**，用户口中的「锁高频音」应是它（代码里没有对高频单独加锁的任何逻辑）。
- 限幅器是**整条信号一个增益**（`dsp.h:480` 注释即「不分频段」），释放时间常数 80 ms（`relLimCoef_`，按 32 样本控制块折算）。

### 2.2 测量方法（`tools/probe_limiter.cpp`）

真实 PUBG 素材（Wwise 解码 48 kHz）：

| 用途 | 素材 | 特征 |
|---|---|---|
| 长尾枪声 | w2522402869 | 3.21 s，峰值 −3.2 dBFS |
| 短促枪声 | w3144728661 | 1.86 s，峰值 0 dBFS，瞬态 71 dB |
| 脚步 | w2253900037 | 0.19 s，mid 占 0.97（250–2k 主体） |
| 环境底噪 | w2833643493 | 4.88 s，<125 Hz 占 0.78 |

场景：底噪 −18 dBFS 铺满 7 s + 脚步每 400 ms（峰值 −20 dBFS）+ t=1.00 s 一发满刻度枪声。
关键：把限幅的影响**单独分离**——`bOn=1` 与 `bOn=0` 两条链路的 aOn/env/step 完全相同，相减即限幅净贡献，不含环境抑制的静态衰减。

### 2.3 结果 A：压缩窗口与脚步衰减（长尾枪声 3.21 s）

| 上限 | 最大压缩 | 压缩持续 | 相对枪声结束 | 窗口内脚步平均被压 | 窄带(1.2k)与全带衰减差 |
|---|---|---|---|---|---|
| 0 dBFS (100%) | 0.0 dB | 0 ms | — | — | 0.00 |
| −3 (≈63%) | −1.8 dB | 2630 ms | −577 ms | 0.0 dB | −0.03 |
| −6 (≈45%) | −4.6 dB | 2880 ms | −327 ms | −0.5 dB | −0.07 |
| −9 (≈29%) | −7.5 dB | 3020 ms | −187 ms | −1.4 dB | −0.13 |
| −12 (≈14%) | −10.3 dB | 3190 ms | −17 ms | −2.8 dB | −0.17 |
| −18 | −16.3 dB | 5700 ms（连底噪一起压） | +2493 ms | −3.9 dB | +0.02 |
| −24 | −22.3 dB | 5980 ms | +2773 ms | −8.0 dB | +0.02 |

短促枪声（1.86 s）同样测：压缩只持续 90–210 ms；到 −18/−24 才变成长时间全程压缩。

**读法**

- 「从枪声响起到尾音结束」→ **属实**。长尾枪声在 −3…−12 dBFS 上限下，增益下降覆盖 2.63–3.19 s，几乎整段尾音；上限越低，窗口越长，直到把底噪也压住（−18 起变成持续压缩）。
- 「掩盖脚步及其他低频声音」→ **部分属实**。窗口内脚步被压 −0.5…−8 dB（平均），个别帧到 −10 dB 以上，绝对可闻度确实下降。上限 100% 时完全无此现象。
- 「专门压低频/脚步」→ **不属实**。1.2 kHz 窄带信号与全带的衰减差 ≤0.17 dB，说明**全带等比压缩**，脚步与枪声的比例丝毫未变（<0.2 dB）。不存在频段选择性的新增掩蔽。

### 2.4 结果 B：枪声变闷了吗（峰值对齐测量）

| 枪声 | 上限 | 起音峰值 | 尾音 RMS(80–400 ms) | 起音−尾音 | 4–16k/40–300 比 |
|---|---|---|---|---|---|
| 短促 | −6 | −0.5 dB | −1.2 dB | **+0.7** | −0.2 dB |
| 短促 | −12 | −0.7 dB | −2.4 dB | **+1.6** | −0.5 dB |
| 长尾 | −6 | −0.2 dB | −1.1 dB | **+0.9** | 0.0 dB |
| 长尾 | −12 | −0.4 dB | −5.3 dB | **+4.9** | 0.0 dB |

- 频谱几乎没动（高低频比变化 ≤0.5 dB）→ **没有被低通，不是「闷」**。
- 起音几乎不降、尾音降得多 → 瞬态/持续比**升高**，听感是更薄、更干脆。
- 所以「闷响」不是限幅器造成的频谱变化。真实的「闷/被捂住」来自：**整段尾音与混响被压平**（空间感消失）+ 上限设得低时整局长时间处在压缩态、动态被压扁。

### 2.5 真正的「脚步听不见」元凶之一：脚步增强自己关掉了

`dsp.h:472` 的 `guard = clamp((−6 − edb)/12 + 1, 0, 1)` 会在该频段电平高时把增强量归零。实测尾音期间瞬态判据输出：

```
t=1.00s trSm=0.12  boost=0.6 dB   （枪声响）
t=1.10s trSm=0.00  boost=0.0 dB
…  尾音全程 trSm=0.00，boost=0.0 dB  …
t=3.40s trSm=0.31  boost=1.6 dB
```

也就是说：**枪声+尾音这 2–3 秒里，脚步增强（+8 dB）是完全关闭的**。这比限幅的影响更大、更直接。叠加「整体被压低 3–14 dB」，才有了用户说的「脚步全没了」。

### 2.6 修复建议

| 优先级 | 改动 | 效果 |
|---|---|---|
| 高 | 尾音期间不要关掉 band2 增强：把 `guard` 从「该频段绝对电平」改为「相对中频/低频占比」或加慢释放，枪声结束后 80 ms 内恢复 | 直接找回被埋的脚步 |
| 高 | 释放 80 ms → 30–40 ms，或做两段释放（快段 20 ms 放掉峰、慢段 200 ms 收尾） | 压缩窗口缩短，尾音不再被整段压住 |
| 中 | 上限低于 −15 dBFS 时在面板给警示（当前 UI 1% = −36 dBFS 完全合法） | 避免用户把整局动态压扁后归咎于软件 |
| 中 | 若目标是「枪声不炸耳、脚步保留」，必须做**频段选择性**限幅（只压 2–5 kHz 枪声带 + 全带轻限幅兜底）；当前单增益架构做不到 | 从根上消除「枪声一响全场景变小声」 |
| 低 | 面板文案加一句「上限越低，枪声期间全场声音一起变小」 | 降低误解 |

## 4. 方案评估：只压 2–5 kHz 枪声带可行吗

用真实素材的功率谱做假设性频带增益推演（`tools/probe_bandsel.cpp`，不改 DSP）。

### 4.1 2–5 kHz 在各声音里的分量

| 声音 | 2–5k 能量占比 | 2–5k 的 A 加权占比 | 压 12 dB 后感知电平 | 谱心变化 |
|---|---|---|---|---|
| 枪声 A 短促 | 15.9 % | 26.9 % | **−1.3 dB** | +315 Hz |
| 枪声 B 长尾 | 47.8 % | 51.2 % | **−2.8 dB** | +15 Hz |
| 脚步 近（0.6–2k 为主） | 4.6 % | 6.2 % | −0.3 dB | −70 Hz |
| 脚步 中（清脆型） | 56.6 % | 60.2 % | **−3.6 dB** | −302 Hz |
| 环境 低频 | 1.9 % | 16.6 % | −0.7 dB | −50 Hz |

### 4.2 三条结论

1. **压不住炸耳**。2–5k 只占枪声 16–48 %，压 12 dB 只换来 −1.3…−2.8 dB 的感知电平；改成 2–8k 也只有 −3.1…−5.3 dB，且长尾枪声谱心掉 1749 Hz（明显变闷）。用户会继续把上限往下拉补偿 → 全带压缩的老问题回归。
2. **掩蔽没被解决**。枪声能量仍有 24.9–27.1 % 落在 250–2k（脚步带）、12 % 落在 <250，2–5k 限幅完全不碰这两块 —— 该掩蔽还是掩蔽。
3. **音色变化因素材而异**。靠近脚步只 4.6 % 在 2–5k，几乎不变；清脆脚步 56.6 % 在 2–5k，压 12 dB 后掉 3.6 dB、谱心 −302 Hz 变闷。同一局里不同脚步音色变化不一致，比"统一变闷"更难接受。

### 4.3 工程副作用

- 现分频点是 150/600/3k，2–5k 不是现成频段：要新增 2k/5k 两处交叉，6 段 LR4 的全通相位补偿必须重标定，否则**静态染色**（所有声音，不只是枪声）。
- 每段独立 lookahead 会打乱块内相位，求和后重新出现过冲（现有机构已为此加硬钳位兜底）。
- 2–5k 是人耳最敏感区（也是方位/距离线索所在）。动态压它 = 交火时该频段"呼吸"，定位线索被调制。
- **兜底悖论**：保留全带砖墙 → 枪声时全场景照样一起变小；去掉 → 削顶爆音。

### 4.4 更优解：枪声事件 duck + 脚步带保持

| 环节 | 做法 |
|---|---|
| 枪声检测 | 复用现有 tilt + 中频瞬态 + 谱平坦度（枪声是宽带、平坦、陡起） |
| 增益 | 事件期间全带 −3…−6 dB，attack 10–20 ms，release 150–200 ms |
| 补偿 | 同时把 250–2k 抬回 0 dB（相对保持），避免脚步被一起拖下去 |
| 兜底 | 砖墙上限仍留，但只在真峰值（≥ −1 dBFS）动作，不参与"变小声" |
| 必做的两处低风险修复 | ① 尾音期间不关 band2 增强（guard 改相对量）② 释放 80 → 30–40 ms |

## 5. 已实施修复（v1.3.0）

### 5.1 改动

| 文件 | 改动 |
|---|---|
| `src/dsp.h` | 新增「枪声事件 duck」：命中后 4 ms 内把 **band0(<150 Hz) 与 band3(>3 kHz)** 各压 4 dB、180 ms 放开；**band1/band2(150–3 kHz) 完全不动** |
| `src/dsp.h` | 判据 `>5k 能量占比` × `全带瞬态`，再加**峰值门控**（本块输入确实顶到用户设的天花板才动作） |
| `src/dsp.h` | 与脚步判据互锁：`trSm > 0.25` 时不做 duck |
| `src/dsp.h` | 新增一路 5 kHz 高通探测支路（单声道，1 biquad + 1 包络） |
| `src/dsp.h` | 限幅释放 80 ms → **35 ms** |
| `res/app.rc`、`res/app.manifest`、`README.md` | 版本 1.2.0 → **1.3.0**（不覆盖 v1.2.0 的 tag 与发行包） |

### 5.2 全量实测把设计改了两次（重要）

见第 6 节：全量 11 043 条素材扫描后发现，**「>5k 占比 + 陡起」这两个条件在素材库里 66 % 的文件上都成立**
（连 0.03 s / −28 dBFS 的小点击都满档）。也就是说，用 2 条枪声标定出来的判据并不能"识别枪声"——
射击游戏的音效本来就有 52 % 是明亮宽带瞬态（枪声/破片/玻璃/弹壳）。

最终设计不再声称"识别枪声"，而是绑定到 duck 真正的目的：

> **信号确实顶到用户设的天花板时，替限幅器分担一点，只削 <150 Hz 与 >3 kHz 两端。**

于是加了峰值门控：没顶到天花板 → 一点都不动；顶到了 → 按判据压两端。深度也从 6 dB 降到 4 dB。
实测触发率从 66 % 降到 **21.7 %**（3.4 h 音频），且全部是真正过载的块。

| 短促枪声 −12 dBFS | 压缩持续时间 | 210 ms | **130 ms** |
| 长尾枪声 −6 dBFS | 最大压缩 | −4.6 dB | **−4.3 dB** |

| 枪声 4–16k / 40–300 比 @−6 dBFS | | 0.0 dB | **−2.0 dB**（炸耳感下降） |


T4 的宽带噪声突发在新判据下会被当成枪声（>5k 占比 >0.36），曾把增强从 +6.4 掉到 +4.9。
处理方式是加「与脚步判据互锁」而不是改测试：`trSm > 0.25` 时不 duck —— 判据 2 说这是脚步类事件，
本来就该抬不该压。实测枪声全程 `trSm = 0`，所以互锁不影响对枪声的作用，T4 回到 +6.4。

### 5.5 这次没有解决、也解决不了的

- **重叠掩蔽**：枪声尾音在 250–2k 的能量仍占 25–27 %，与脚步同频同时，任何滤波/限幅都无法把两者分开。
  上限低于 −12 dBFS 时，尾音整段高于天花板，限幅只能继续压 —— 这时"全场景变小声"是限幅器在履行它的定义。
- duck 对**脚步电平**的保护只有 0.4–0.6 dB（真正的收益在"压缩窗口缩短一半"和"炸耳感降 2 dB"）。
- 因此配套改了文案与 FAQ：**上限建议 −3 ~ −6 dBFS，别当音量旋钮用**。

## 6. 全量测试（11 043 条 / 17.2 h）

### 6.1 工具与速度

`tools/fullscan.exe <list.txt> <out.csv> [线程数] [vgmstream 路径]`

| 项 | 值 |
|---|---|
| 规模 | 11 043 个 wem，2.9 GB，解码后 **17.23 h** |
| 可解码 | **11 043 / 11 043**，失败 0（965 条加密、14 条解码器不支持已在抽库阶段剔除，见 6.3） |
| 墙钟 | **257 s**（14 线程）= **241× 实时** |
| 单文件成本 | 解码 90 ms + 进程启动 ~30 ms + DSP 20 ms |
| DSP 单独 | 290× 实时（单核 0.35 %） |
| 数据通路 | `vgmstream-cli -i -w -p` 直连管道，**不落盘**（否则要写 30 GB 临时 wav） |

瓶颈在解码进程启动，不在 DSP：DSP 用 14 核可跑 4 000×，实际只有 241×。
要再快只能把 vgmstream 静态链进来（省掉 11 043 次进程创建），预计能到 700–900×。

### 6.2 抽样覆盖结论：**形态上没偏，数量上远远不够**

| 形态（按素材声学特征） | 全量 | 632 条子集 |
|---|---|---|
| A 明亮宽带（枪声/破片/玻璃/弹壳） | 52.1 % | 51.3 % |
| A- 偏亮宽带 | 32.1 % | 32.6 % |
| B 中频瞬态（脚步/换弹/碰撞） | 6.7 % | 8.7 % |
| C 低频独大（环境/载具/风） | 2.3 % | 2.5 % |
| D 其它（持续/人声/UI/音乐） | 6.9 % | 4.9 % |

- `features.json` 只解码了 **632 / 11 043 = 5.7 %**，调参又只用了其中 189 条。
- 好在形态分布与全量吻合（±2 个百分点）→ **抽样本身没有系统性偏差**。
- 但"战斗声音"的绝对样本量太少：`docs/01` 里「明亮瞬态（枪声/破片/玻璃）」只有 **8 条**、
  「极低频瞬态（爆炸/车门）」**8 条**，而全量里带明亮宽带成分的素材有 **5 751 条**。
  判据等于用 8 条样本去代表一个 5 751 条的总体 —— 这就是 5.2 那次翻车的根因。
- **结论：样本包含了各类战斗声音的形态，但密度远远不够；枪声/爆炸类必须按全量重标定。**

### 6.3 那 965 条解不开的文件：查清了，是加密不是抽取错误

先给结论：**`carve.py` 的 offset/size 没有错**，pak 里就是那么多字节。

证据（`tools/carve_check.py`，全 pak 去重扫一遍）：

| 项 | 数量 |
|---|---|
| 去重后的 Wwise 头 | **12 023** |
| 内部 chunk 链能走到 `data` 块（可解码） | **11 057** |
| 帧头之后即密文、读不到 `data` 块 | **965** |
| 链表越界（pak 末尾那条） | **1** |

对第 12 023 条做定点核对：RIFF 头声明的长度 = 抽出来的长度，pak 里其后 64 KB 内没有下一个 `RIFF`，
所以不是"少读了"，而是这个 wem 在 pak 里就这么长。

真正的差异在**帧头之后的内容**：

```
正常：RIFF WAVE → fmt(0x42) → smpl → data ...     每个 chunk id 可读
异常：RIFF WAVE → fmt(0x42) → ?? ?? ?? ?? ...     之后全是高熵字节，chunk id 读不出来
```

`RIFF/WAVE/fmt=0x42/codec=0xFFFF/采样率` 全是明文且正确 —— 这是 Wwise **AES 加密媒体**的典型形态：
只保留引擎识别编码所需的前缀，其余加密。`vgmstream` 没有 key，只能报 `no 'data' tag found`。
另外这 965 条的 offset 在 pak 里成段聚集，符合"按 bank/区段加密"的做法。

顺带修正一个口径错误：`docs/01` 里写的「13 590 条流」是 **扫描命中次数**，`carve.py` 的 32 MB 窗口有
4 MB 重叠，边界附近的头被数了两次；去重后是 **12 023 条**。文件数一直是对的（名字用绝对 offset，重复写同一文件）。

已改的 `carve.py`：

| 改动 | 原因 |
|---|---|
| 校验内部 chunk 链能否走到 `data` | 只验 4 个字段分不出加密文件，会把死文件写进素材库 |
| 加密/链表不可读的条目写进 `samples/encrypted.txt`，不写 .wem | 让"库里有哪些不可用"变成可查的事实 |
| 用 `seen` 集合按绝对 offset 去重 | 消除 4 MB 重叠造成的重复计数 |
| pak 末尾的文件按剩余长度读，不再整条丢弃 | 捞回第 12 023 条（实测它的 data 块落在 pak 之外，本质仍是残片） |
| 删除 `data[-8:-4] in (b'data',) or True` | 原式恒为真，等于没有校验 |

试跑验证：新脚本产出 **11 057** 个，与旧库里可解码的那批**逐个一致**（无新增、无缺失），
多余的正好 965 个 = `encrypted.txt`。所以现有素材不需要重抽，只是要知道有 8 % 是不可用的。

未做：那 965 条要解出来必须有 Wwise 的 AES key（在游戏的 `AudioDevice`/bank 定义里，属于绕过保护，
不在本项目范围）；因此**覆盖率上限就是 11 057 / 12 023 = 92 %**，这一点写进结论。

另外修掉了 `fullscan` 的一个副作用：`vgmstream -w -p` 会把 PCM 写进管道，**同时**在源文件旁落一个
`<infile>.wav`，11 043 条全跑一遍就是 13 GB 垃圾（本次已清理）。现在读完立刻删除。

### 6.5 清理结果与最终口径

| 步骤 | 数量 |
|---|---|
| pak 内唯一 Wwise 头 | 12 023 |
| − Wwise AES 加密（无 key 不可解） | −965 → 删除 |
| − 结构合法但本机解码器拒绝（含 1 条越界残片） | −14 → 移到 `samples/wem_unreadable/` 留档 |
| **samples/wem（全部可解码）** | **11 043** |

复跑确认：**11 043 / 11 043 全部解码成功，削顶 0、非有限样本 0，241× 实时**。
覆盖率上限 = 11 043 / 12 023 = **92 %**（缺口全部来自加密，属素材侧限制）。

`samples/encrypted.txt` 保留为可查清单；`carve.py` 以后再跑也不会把它们写进素材库。
